DIAGNOSTICO, ARQUITECTURA Y PLAN DE MIGRACION
CRONOPIOS - WEBAPP ACADEMICA
==============================================

Este documento resume la inspeccion del proyecto existente, el diagnostico
tecnico, la propuesta de arquitectura, los riesgos y el plan de migracion.

No se modificaron archivos de codigo como parte de este diagnostico.


1. STACK DETECTADO
------------------

- Next.js 14 con App Router.
- React 18.
- TypeScript estricto.
- Tailwind CSS.
- Supabase SSR y cliente browser.
- Framer Motion.
- Lucide React.
- PDF.js.

La configuracion TypeScript esta en:

- tsconfig.json

Caracteristicas principales:

- strict: true
- noEmit: true
- alias @/* para la raiz del proyecto
- moduleResolution bundler

6. SUPABASE Y ESQUEMA
---------------------

El esquema principal esta en:

- supabase/mvp-schema.sql

Tablas principales:

profiles

- id
- full_name
- degree
- curriculum
- timestamps

subjects

- id
- name
- code
- year
- semester
- curriculum

correlatives

- subject_id
- required_subject_id

user_subjects

- user_id
- subject_id
- status
- grade
- passed_at
- timestamps
- constraint unica por usuario y materia

community_posts

- Publicaciones de la comunidad.
- Politicas RLS configuradas.
- Existe un helper para consultarlas, pero la pagina actual usa datos
  estaticos.

RLS:

- profiles limitado por auth.uid().
- subjects disponible para usuarios autenticados.
- correlatives disponible para usuarios autenticados.
- user_subjects limitado al usuario autenticado.
- community_posts limitado a publicaciones vigentes.


7. PROBLEMAS DE CONSISTENCIA
----------------------------

1. Hay seeds parcialmente duplicados entre:

- supabase/mvp-schema.sql
- supabase/seed-subjects.sql
- supabase/seed-curricula.sql

2. La columna curriculum fue agregada posteriormente y puede no existir en
   instalaciones remotas que no hayan ejecutado todos los scripts.

3. Las definiciones de planes y correlatividades estan repartidas entre
   varios archivos SQL.

4. Conviene estabilizar el modelo y documentar el orden de ejecucion de
   scripts antes de ampliar cambios estructurales.

No se recomienda modificar el esquema durante la primera etapa visual.


8. DUPLICACION ENTRE RECORRIDOS
--------------------------------

/recorrido:

- Es publico.
- Usa materias hardcodeadas.
- Utiliza SubjectItem.
- No consulta Supabase.
- No refleja notas, planes ni correlatividades reales.
- Es una demo estatica.

/dashboard/materias:

- Es autenticado.
- Usa Supabase.
- Incluye los dos planes.
- Importa analiticos.
- Maneja notas y estados.
- Maneja correlatividades.
- Persiste datos.

Conclusion:

La fuente real debe ser materias-manager.tsx.

La ruta principal futura debe ser:

- /dashboard/recorrido

Durante la migracion:

- /dashboard/materias debe redirigir o renderizar el mismo modulo.
- /recorrido debe redirigir a login o transformarse en una landing
  explicativa sin datos academicos falsos.


9. PROBLEMAS FUNCIONALES ACTUALES
---------------------------------

Dashboard:

- Ya filtra avance por el plan seleccionado usando una cookie.
- Calcula materias aprobadas y promedio.
- No muestra claramente el nombre del plan.
- No muestra de forma directa las materias disponibles segun correlativas.

Calendario:

- Usa datos hardcodeados.
- Muestra diciembre de 2024.
- La informacion puede estar obsoleta.
- No consulta community_posts.
- No tiene estados de carga o error porque no consulta datos.

Esto representa un riesgo porque el producto necesita fechas academicas
actuales.

Guia de catedras:

- Tiene busqueda funcional.
- Usa datos reales locales.
- Conserva fuentes oficiales.
- No tiene necesariamente todos los datos de sede y horarios.

Comunidad:

- Usa publicaciones hardcodeadas.
- No reutiliza getPublishedCommunityPosts().
- Esta fuera del dashboard.
- No aparece en la navegacion principal.

Autenticacion:

- Login y registro funcionan con Supabase.
- La marca sigue siendo trama.
- Los formularios no son componentes compartidos.
- No hay perfil/configuracion visible.
- El plan no se selecciona durante el registro.
- La seleccion de plan se persiste actualmente desde materias mediante
  localStorage y cookie.

15. RIESGOS
-----------

Riesgos altos:

1. Cambio de rutas.

Puede romper enlaces, favoritos, redirecciones y pruebas manuales.

Mitigacion:

- Mantener redirects temporales.

2. Datos de dos planes.

user_subjects no guarda explicitamente el plan. El plan se deduce por
subject_id.

Hay que cuidar:

- Cambio de plan.
- Importacion de un analitico viejo en el plan nuevo.
- Materias equivalentes entre planes.

3. Correlatividades alternativas.

El plan nuevo incluye opciones y recorridos alternativos. Una regla simple
de "todas las correlativas" puede ser insuficiente para modelar:

- Opciones A o B.
- Nucleos completos.
- Recorridos alternativos.
- Seminarios optativos.

Riesgos medios:

- Calendario obsoleto.
- Migracion parcial de la marca.
- Componente materias-manager.tsx demasiado grande.

Riesgos bajos:

- Homogeneidad visual entre tarjetas.

- Nuevo components/app-shell/dashboard-header.tsx

Fase 2 - Navegacion

- Mobile con Inicio, Recorrido, Agenda y Catedras.

Fase 3 - Recorrido academico

- Crear /dashboard/recorrido.

- Reutilizar la logica actual.
- Mantener /dashboard/materias como compatibilidad.
- Eliminar progresivamente el recorrido estatico hardcodeado.

Fase 4 - Inicio academico

Mostrar rapidamente:

- Avance.
- Promedio.
- Materias disponibles.
- Proxima fecha.

Reutilizar consultas existentes y no duplicar reglas.

Fase 5 - Agenda y catedras

- Redisenar visualmente sin inventar datos.
- Mantener contactos oficiales.
- Definir fuente de fechas antes de mostrarlas como actuales.
- Separar componentes de agenda y catedras.

Fase 6 - Refactor interno

Extraer gradualmente de materias-manager.tsx:

- Selector de plan.
- Filtro de materias.
- Estado de materia.
- Reglas de correlatividad.
- Importador de analitico.
- Resumen de avance.

Cada extraccion debe conservar los mismos tipos y comportamiento.

Fase 7 - Validacion

Despues de cada fase:

- npm.cmd run build
- npm.cmd run lint

Ademas probar:

- TypeScript.
- Responsive mobile.
- Navegacion.
- Login y logout.
- Cambio de plan.
- Importacion.
- Destildado.
- Notas.
- Correlatividades.

17. RECOMENDACION
-----------------

La primera implementacion recomendada es la Fase 1:

- Shell.
- Navegacion.
- Marca.
- Tokens visuales.

Esto permite establecer la identidad Cronopios sin tocar inicialmente la
logica academica.

Luego conviene migrar el recorrido real a /dashboard/recorrido, manteniendo
/dashboard/materias como ruta compatible hasta comprobar que todas las
funciones siguen operativas.
